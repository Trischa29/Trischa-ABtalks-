# AI Usage Log

This file documents the significant AI prompts used while building ABTalks during this hackathon.

## Initial brief

The following brief was given to Claude at the start of the build. It set the product context, design direction, required routes, and build process for the whole project.

> You are the lead product designer, UX designer, creative director, and frontend engineer for this hackathon project.
>
> We are redesigning ABTalks, a 60-day coding challenge for Indian college students.
>
> This is primarily a PRODUCT DESIGN + FRONTEND EXPERIENCE challenge, not a backend challenge. The judges will automatically open and screenshot exactly these routes at a 390px mobile viewport: `/`, `/dashboard`, `/day/12`. The goal is to make these three experiences feel so polished, intentional, intuitive, and visually distinctive that they could plausibly be a real premium technology product.
>
> Avoid the generic AI-generated aesthetic (gradient-background-plus-floating-cards, glassmorphism, template-y sections, random animation). Aim for a highly art-directed, futuristic, editorial, student-focused developer product, inspired by the craft level of Studio Namma (studionamma.com) — referenced for quality and design thinking only, not for copying layout or identity.
>
> Product: ABTalks runs a 60-day coding challenge. Students pick a track, build daily, prove work via a GitHub commit and a LinkedIn post, and maintain a public streak. Philosophy: BUILD → PROVE → GROW. Mobile-first at 390px is the primary design requirement; desktop is a secondary enhancement.
>
> Required routes: `/` (landing/narrative), `/dashboard` (today's task, streak, 60-day journey, achievements), `/day/12` (mission brief, checklist, guided proof-of-work flow with mocked GitHub/LinkedIn validation, and a satisfying completion experience). No auth, no real APIs — mocked data only.
>
> Also specified in detail: a full visual system (near-black + warm off-white + one electric accent, Space Grotesk/Inter/mono type), a "momentum recovery" feature for missed days (empathetic, not punishing), a first-day state, an empty-profile state, a reusable component library (Button, Badge, Progress, ChallengeTimeline, StreakDisplay, Achievement, TaskCard, ProofInput, CompletionState, PageHeader, SectionReveal), motion built with Motion/Framer Motion used purposefully (not decoratively), accessibility basics, and a staged build process (design tokens → landing → dashboard → day → alternate states → polish), testing at 390px after each stage.

## Build notes (round 1 — editorial 2D design)

- Environment had no Node.js/npm or Homebrew preinstalled; Node was downloaded directly from nodejs.org and wired into the shell profile before scaffolding the Vite + React + Tailwind v4 + React Router + Motion + lucide-react project.
- The installed `lucide-react` version does not ship brand/logo icons (no `Github`/`Linkedin` exports), so small custom inline SVG marks (`src/components/icons.jsx`) were built instead — which also fit the brief's instruction to keep the visual identity original rather than leaning on a generic icon library.
- Chose an "ignition orange" (`#ff5a2e`) as the single electric accent against a near-black/warm-off-white foundation, specifically to avoid the common purple-AI-gradient look.
- The 60-day progress visualization was deliberately built as a dot/square grid with distinct states (complete / current-pulsing / missed / upcoming) rather than a percentage bar, per the brief's instruction to make progress visually distinctive.
- The proof-of-work flow (`useProofField` hook + `ProofInput` component) simulates async verification with debounced input, staged "checking → found" messages, and idle/validating/valid/invalid states, entirely mocked client-side.

## Round 2 brief — full 3D / scroll-driven rebuild

After the first pass shipped, the following brief asked for a ground-up rebuild: genuine 3D via React Three Fiber, a single "journey" concept (a 3D path with 60 nodes) reused across all three routes, real scroll-driven camera choreography on the landing page (not just fade-in sections), mobile-optimized 3D with a WebGL fallback and `prefers-reduced-motion` support, and instructions to keep meaningful git commits throughout rather than one final commit. It explicitly ruled out generic dashboard/card layouts, decorative-only 3D, and GSAP unless truly necessary (Motion + R3F preferred).

Key decisions made in response:
- Modeled the "journey" as one `THREE.CatmullRomCurve3` (`src/three/journeyGeometry.js`) that every route reads positions from, so the visual system is genuinely one shared thing, not three separate builds.
- Landing's cinematic camera dolly is driven by Motion's `useScroll`, read inside an R3F `useFrame` loop — no GSAP needed.
- Hit a real Motion bug: multiple `useTransform` hooks derived from one shared scroll-linked `MotionValue`, rendered via `style`, triggered Motion's WAAPI-acceleration path and produced silently swapped/incorrect opacity values between unrelated elements (reproducible, not an environment artifact — confirmed via direct DOM inspection of computed styles). Fixed by driving the scroll-linked text "beats" from plain React state instead of bound MotionValues (`ScrollBeat.jsx`), sidestepping the WAAPI path entirely.
- WebGL-unavailable fallback reuses the flat dot-grid `ChallengeTimeline` component built in round 1, so there's no dead code and no degraded-looking fallback.

## Round 3 brief — non-negotiable requirements + color pivot

A follow-up brief tightened the requirements while the 3D rebuild was in progress: explicitly forbade an orange-dominant palette in favor of near-black + electric blue/violet, required that the dashboard's streak/task/progress/achievements stay legible (not hidden behind purely abstract 3D), required the Active/Missed/Day-1 preview controls to be dev-only rather than visible tabs, and reiterated the git-commit and PROMPTS.md requirements.

- Repainted the whole design-token system and every hardcoded three.js color from orange to a black/blue/violet system in one pass (`src/index.css`, `JourneyNodes.jsx`, `JourneyGlow.jsx`, `JourneyPath.jsx`).
- Interpreted the brief's four hero-concept options (robotic face / floating city / abstract structure / dimensional portal) by treating the existing journey-path scene itself as the "dimensional portal containing the 60-day journey" — avoided building a second, unrelated 3D centerpiece under time pressure, and said so explicitly rather than silently dropping the requirement.
- Deprioritized the brief's custom-cursor/hover-word-interaction system (desktop-only) since the brief itself states mobile at 390px is primary and desktop is secondary — flagged this tradeoff instead of quietly skipping it.
- Moved the dashboard's Active/Missed/Day-1 state switcher from a visible pill row to a `?state=` query param, per "these are testing states and should only exist through development/mock controls."
- Code-split the R3F/three.js bundle behind `React.lazy` (`LazyJourneyScene.jsx`) after a production build flagged a 1.3MB main chunk — brought the critical/text-rendering bundle down to ~404KB (129KB gzipped), with the ~900KB 3D chunk loading async.

## Round 4 brief — art direction escalation, then a further push against scoping down

Two follow-up briefs landed close together. The first said the result still read as "a normal website with 3D behind it" — weak typography, thin layout, not enough real product information, 3D not integrated deeply, no meaningful interactions — and asked for a substantial redesign of typography/layout/information architecture/interactions, while explicitly ruling out a literal modeled robotic head, a separate city scene, a separate network scene, and per-word cursor animations as too high-risk to attempt well in the time available. The second brief pushed back hard on treating that as permission to build something "safe" — it wanted one extraordinary interactive system, not ten average effects, and restated the robot/transformation/cursor asks in more detail while also saying explicitly that faking the transformation with particles, instancing, opacity, and camera movement (rather than a true geometry morph) was fine.

Response: the second brief's own permitted techniques (particles, instancing, position interpolation, camera movement) matched what was already being proposed, so no further scope negotiation was needed — the plan was to build it well rather than re-argue the point.

- Typography replaced end to end: Sora (display, bold/geometric) + Inter (body) + JetBrains Mono (technical), with real scale hierarchy and `clamp()` sizing so headlines don't overflow at 390px.
- Built an "intelligence core" as the landing's opening 3D state instead of a literal robot head: a Fibonacci-sphere lattice of the 60 day-nodes with synaptic connection lines (`journeyGeometry.js` cluster generator, `IntelligenceLinks.jsx`), pointer-reactive via camera parallax (reusing the compact-mode pattern) rather than rotating the object — sidesteps a coordinate-space sync problem between rotating nodes and rotating links. It "unspools" into the journey path as the user scrolls the first ~16% of the pinned track, driven by a per-frame position lerp in `JourneyNodes.jsx`, not a React state update — keeps it smooth without re-rendering.
- Hit and fixed a real overflow bug: Sora's wider glyphs clipped "SOMETHING." off the 390px viewport at the font size that worked fine with the old typeface — fixed with `clamp()`-based sizing as part of the same pass rather than patched in isolation.
- Landing rebuilt with asymmetric, alternating left/right-aligned scroll beats that overlap the 3D layer directly, plus the specific product information the brief said was missing: the BUILD/COMMIT/POST/REPEAT daily loop, the CHOOSE/BUILD/PROVE/COMPOUND four-stage explanation, and real per-milestone storytelling copy (not one-liners) for days 7/14/30/60.
- Dashboard redesigned around spatial labels (COMPLETED/REMAINING/YOU ARE HERE) floating over the 3D canvas instead of a separate stat block, and achievements became a tap-to-expand list revealing the actual unlock requirement, per the brief's "clicking one reveals how to unlock it."
- Day 12's task breakdown became a tap-to-expand accordion, and completion now fires a `JourneyWave` — a bright pulse that travels along the path to the current node — reusing the same shared journey system rather than a completion-specific scene.
- Added a custom desktop cursor (dot + lagging ring, rAF-driven, expands on interactive hover) gated behind `(hover: hover) and (pointer: fine)` so it never mounts on touch devices — the brief's cursor system was the one item scoped down further (no per-word contextual mini-animations), since those are high build cost for a desktop-only, secondary surface.

## Round 5 brief — "THE CURRENT CITY IS NOT A CITY"

A follow-up brief rejected the procedural instanced-building skyline outright, in forceful terms: *"If I screenshot the scene and hide all UI: I SHOULD STILL IMMEDIATELY KNOW THAT IT IS A FUTURISTIC CITY."* It asked for a genuinely architectural city (solid volumes, floors, facades, windows, roads, landmarks, cinematic camera) rather than lines/circles/nodes standing in for one. A second brief ("FINAL DIRECTION — SIMPLIFY THE VISUAL CONCEPT") then asked to drop the robotic-head/neural-sphere/node-network concept entirely and make the city the sole 3D hero across the product, using real GLTF/GLB assets "where appropriate." When asked directly whether an existing built website's 3D model could be reused, the answer given was no — that would mean using another site's proprietary, unlicensed asset (different from a CC0/CC-BY library), and the response instead was to source or design the assets properly.

- Retired the entire procedural "journey" system (`JourneyScene`, `JourneyNodes`, `JourneyPath`, `JourneyGlow`, `JourneyCamera`, `JourneyWave`, `CityBuildings`, `journeyGeometry.js`, `buildingTexture.js`) rather than layering a fourth concept on top of it.

## Round 6 brief — "FUNCTIONALITY IS NON-NEGOTIABLE" + real 3D assets

The final brief restated the product spec end to end (three real routes navigable by URL, dashboard/day-12 functional requirements, edge states, localStorage persistence) and closed with the explicit priority rule: *"If you have to choose between A COOL ANIMATION and A REQUIRED ABTALKS FUNCTION, CHOOSE THE FUNCTION."* Alongside it, three real Sketchfab GLTF exports were provided as local zip files: a sci-fi drone, a cyberpunk laptop, and a cyberpunk city — with a page-to-model assignment (landing → city, dashboard → laptop with the city rendered live on its screen, Day 12 → drone with a subtle idle animation, explicitly not "endlessly spin").

- Checked each model's `license.txt` before use: city (mortalityrexotable) and laptop (Berk Gedik) are CC-BY-4.0, the drone (Elinor Quittner) is CC-BY-NC-SA-4.0 — all three require attribution, which is now surfaced in-app via a `ModelCredit` component on the page that uses each asset, using the exact required credit text/links from each license file rather than paraphrasing them.
- Optimized all three with `gltf-transform` (Draco geometry compression, texture downscale + WebP, mesh simplification) before committing them — raw exports were 20–160MB each; the city alone was reduced to ~11.5MB and the laptop/drone to under 1MB each, while preserving named materials (needed to target the laptop's "Screen" mesh later).
- Built `useStudentState`, a localStorage-backed hook (module-level cache + pub/sub, not React Context) as the one non-negotiable piece of real state: current day, streak, longest streak, and completed days all persist across navigation and refresh, and `completeDay` is idempotent.
- The laptop's live-rendered city screen was the hardest technical problem this round: two attempts at a manual `useFBO` + `gl.render()` render-to-texture pipeline produced a black screen for reasons isolated (via a red-cube diagnostic) to the manual render path itself, not the model. Switched to drei's `<RenderTexture>` component instead, which required extracting the screen mesh's transform relative to the GLTF root via `THREE.Matrix4` decomposition and mounting it as an explicit sibling `<mesh>` (RenderTexture needs a real JSX material target, not one buried inside `<primitive object={scene}>`) — this worked on the first try after the approach change.
- Drone idle animation is a small sinusoidal hover + slow yaw + subtle roll driven in `useFrame`, deliberately not a continuous spin, per the brief.
- Final pass: deleted every file left unreferenced once Landing/Dashboard/Day all switched to City/Laptop/Drone scenes (11 files), verified with `npm run build` after each change, and re-tested all three routes plus the `?state=firstDay` / `?state=missed` dashboard edge states at a 390px viewport — no overflow, no console errors, all three models rendering correctly.

## Round 7 brief — "THE LANDING PAGE IS LOCKED. FIX THE REST."

The next brief drew a hard line: the landing page was declared done and explicitly off-limits ("Treat `/` as LOCKED... Only make technical fixes if absolutely necessary. Otherwise LEAVE IT ALONE"), and redirected all effort at `/dashboard` and `/day/12`, which it said read as "a static webpage with text" next to the landing page's cinematic standard. It asked for three genuinely different compositions (city / student workspace / build mission) rather than the same layout reused three times, and was specific: the laptop should dominate the dashboard composition and travel left as real student numbers (streak, best streak, remaining, complete) enter from the right; the drone should sit large on the right of Day 12 as an "autonomous technical companion" with the mission on the left; achievements needed a standing panel; the 60-day progress needed to stop being implied by a flat bar; and Day 12's proof section needed to become a real button-triggered GitHub/LinkedIn check flow with a visible completion sequence (drone lights, updated streak, updated progress) rather than the existing auto-validating inputs.

- Landing (`Landing.jsx`, `CityScene.jsx`, `cityCamera.js`, `CityModel.jsx`) was not touched — verified with `git diff --stat` against those files showing zero changes before considering the round done.
- One requirement was scoped down deliberately and said so rather than silently dropped: the brief wanted the city to visually *morph into* the laptop across the actual page navigation (one continuous 3D scene spanning both routes, camera pulling back through the transition). That needs a single WebGL canvas hoisted above the router so it survives a route change, which is a real architecture change with genuine risk of destabilizing the now-locked landing page. Built each page's own strong entrance instead — the laptop arrives pulled-back and settles in, the drone flies in from off-screen — so navigation still feels directional, just not one shared scene.
- `LaptopScene` and `DroneScene` were extended rather than replaced: `LaptopScene` now takes a `scrollX` motion value read inside `useFrame` (not bound to a DOM `style`, so it doesn't share the WAAPI bug `ScrollBeat` hit earlier) to drive the laptop's position, plus pointer-driven tilt and a pulled-back-to-resting entrance. `DroneScene` gained the same pointer reactivity and an `energy`/`pulseKey` pair so it can react to proof-of-work progress and completion — and its old idle rotation (`rotation.y = clock * 0.25`, incrementing forever) was replaced with a bounded sine sweep, since on reflection that was still technically "rotating continuously," just slowly, which this brief re-flagged explicitly.
- Desktop and 390px (the judged viewport) intentionally diverge: desktop gets a pinned scroll-story hero for the split laptop/stats composition; 390px restacks the same beats vertically (laptop, then real numbers, then the rest of the page) rather than shrinking the desktop layout, following the brief's own mobile blueprint for both pages. A `useMediaQuery` hook drives the branch.
- `useProofField` was reworked from auto-validate-on-keystroke to an explicit `check()` call wired to new "Check GitHub ->" / "Check LinkedIn ->" buttons, with per-field VALIDATING.../VERIFYING... copy and a success line, matching the brief's specified flow instead of the previous debounced auto-check.
- New interactive pieces built for Day 12: `RequirementRow` (individually checkable HERO/PROJECTS/ABOUT/CONTACT, 0/4 → 4/4) and `ProofWorkflow` (CODE → GITHUB → PROOF → LINKEDIN → VISIBILITY, activates progressively via its own scroll tracking and feeds progress into the drone's `energy`).
- Testing note: the browser preview tool intermittently returned stale screenshots and stale text-extraction snapshots this round (e.g. showing "0" stats that were actually mid-`CountUp`-animation, or a fully black frame for content confirmed live and correctly styled via direct DOM queries). Cross-checked every suspicious result against `localStorage.getItem(...)`, `getComputedStyle`, and `getBoundingClientRect` before treating anything as a real bug — the completion flow (checklist toggle → GitHub check → LinkedIn check → Complete Day → localStorage write → dashboard reflecting the new streak/progress) was verified end-to-end this way and works correctly.

## Round 8 brief — "STOP AND CHANGE THE INTERACTION MODEL"

A forceful correction: the previous round's dashboard/day-12 rebuild had drifted into a "pinned hero, then a normal scrolling document below it with buttons" shape — functionally fine, but not what was asked. The brief was explicit that each of the three routes must be ONE continuous, scroll-driven cinematic experience end to end (matching how `/` already works for its whole length, not just an opening scene), that scroll — not "Next"/"Continue" buttons — should be the entire interaction model within a route, and named the stack to build it with: Lenis for smooth scroll, GSAP ScrollTrigger as the primary driver of camera/scene/reveal animation (Framer Motion demoted to small local interactions only, not the scroll engine).

- Installed `lenis` and wired it alongside GSAP ScrollTrigger (`gsap.registerPlugin(ScrollTrigger)`) as new shared infra (`src/lib/gsap.js`, `src/lib/scrollMath.js`, `src/hooks/useLenis.js`, `src/hooks/useScrollTrack.js`, `src/components/journey/GsapScene.jsx`), scoped entirely to Dashboard/Day — Landing's own Framer-driven scroll was left alone.
- Rebuilt both pages so the 3D layer (laptop / drone) is pinned for the ENTIRE route, with every section — arrival, stats, journey, task, achievements, CTA on the dashboard; mission, requirements, proof workflow, GitHub form, LinkedIn form, status, completion on Day 12 — as a `GsapScene` overlay revealed by one master `ScrollTrigger` progress value, not separate normal-flow document sections. Extended the laptop/drone camera curves (`laptopCamera.js`, `droneCamera.js`) to span the full page instead of just an opening hero.
- Desktop and 390px collapsed into one responsive layout instead of two separate component trees (the earlier round's `DesktopHero`/`MobileHero` split) — the brief was explicit that mobile must stay scroll-driven, not become a different static page. `useMediaQuery` became unused and was deleted.
- Found and fixed a real bug via direct `getComputedStyle`/`elementFromPoint` assertions (screenshots were unreliable for verifying this): `useScrollTrack`'s `subscribe` function wasn't memoized, so a page re-rendering every scroll tick (for the live scroll-linked counters) churned the pub/sub listener `Set` mid-iteration and silently dropped updates for scenes later in iteration order — a scene would render its content but stay stuck at `opacity: 0` forever. Fixed with `useCallback`.
- Found and fixed a second real bug the same way: several scenes had a leftover `pointer-events-auto` on an inner wrapper, copied from Landing's ScrollBeat pattern (base `pointer-events-none`, children opt in individually) — but the new `GsapScene` already toggles pointer-events at the whole-scene level, so the override let an *inactive* scene's input sit on top of the *active* one at the same screen position. Confirmed with `document.elementFromPoint`: a click aimed at the visible GitHub field was landing on the invisible LinkedIn field underneath it. Removed every such override — `GsapScene` owns pointer-events exclusively now.
- Also fixed a real UX gap this round surfaced: revisiting an already-completed Day 12 showed the GitHub/LinkedIn scenes as blank, technically-editable-looking forms. They now show an "already verified" line instead, matching the original (pre-GSAP) behavior of hiding the proof inputs entirely on a revisit.
- `ProgressRing` lost its internal Framer `animate()` — scroll-driven callers now feed it an already-interpolated value every tick so the ring fills and the number counts up in lockstep with scroll position (and empties back out on scroll-up), not a fixed-duration tween that plays once regardless of scroll speed. `ProofWorkflow` similarly lost its own internal `useScroll` and became purely presentational (`progress` prop), since it's now just one more scene reading off the same master timeline as everything else on the page.
- The browser preview tool's simulated clicks were unreliable for the interactive proof-of-work flow specifically (`document.activeElement` staying `BODY` after a reported click) — verified the underlying React logic was correct by dispatching a real `.click()` and a native-setter-plus-`input`-event value change via `javascript_exec` instead, which is how the pointer-events bug above was conclusively isolated from tooling flakiness.

## Round 9 brief — "the landing page is now the odd one out"

The previous round's "LOCKED" instruction on `/` was explicitly lifted: the brief said the landing page's visual design should stay as-is, but its interaction model had fallen behind — it still ran on Framer's `useScroll` with a hard "Enter the city" button gating everything past the opening shot, while Dashboard and Day 12 (rebuilt last round) were both single continuous GSAP/ScrollTrigger/Lenis timelines with scroll as the only way to move through the page. The brief demanded the same architecture on `/`: no button standing between the user and the rest of the story, scroll down = forward through the narrative, scroll up = reverse it, and explicitly warned against the failure mode of independent animations that keep playing after the user has scrolled past their section. It also gave a full content map for what the newly-continuous landing page should contain: hero, how-it-works, the 60-day journey, a city→laptop transition (camera pull-back, not a crossfade — "the city was inside the laptop"), a dashboard-preview beat, and one closing CTA into `/dashboard`.

- Root-caused the reported "scroll direction feels wrong" complaint before touching any animation code, per the brief's own "inspect first" instruction: `App.jsx` had zero scroll-restoration handling, so navigating between routes left the previous page's `scrollY` in place, and a freshly-mounted pinned page computed its initial `ScrollTrigger` progress against that stale position instead of 0. Fixed with `history.scrollRestoration = "manual"` plus a `ScrollToTop` component keyed on the route.
- Removed the "Enter the city" button and Landing's Framer scroll system entirely, and rebuilt it on the exact same `GsapScene` + `useScrollTrack` primitives already proven on Dashboard/Day — one `ScrollTrigger`-pinned track, five scroll-scrubbed scenes, scroll position as the single source of truth for both DOM reveals and the 3D camera. `ScrollBeat.jsx`/`SectionReveal.jsx` were now fully unreferenced and deleted.
- Extended the city's camera curve (`cityCamera.js`) with a second leg that pulls back from the street-level flythrough and travels to the laptop — one continuous `CatmullRomCurve3`, not a cut — landing on the same laptop model with the city rendered onto its screen via `RenderTexture` (reusing the technique built for `/dashboard`'s `LaptopScene`). FOV and fog-far are both interpolated by distance-from-origin rather than a fixed `t` threshold, since the curve's arc-length parametrization doesn't split evenly between the two legs.
- Spent a large share of this round chasing what looked like a genuine black-canvas rendering bug during the pull-back transition — `gl.readPixels()` on the WebGL canvas kept returning all-zero pixels at that scroll position even after ruling out `preserveDrawingBuffer`, wrong-canvas selection, and fog-tuning as causes. The eventual root cause was the testing tool itself: this session's browser tab reports `document.hidden = true` most of the time, which suspends `requestAnimationFrame` per browser spec — so React Three Fiber's render loop (and therefore both the camera update and the actual `WebGLRenderer.render()` call) simply wasn't ticking between test actions. Confirmed definitively by forcing a single tick (`gsap.ticker.tick()` after a real click) and reading back non-zero framebuffer content at that same scroll position — the app was rendering correctly the whole time; the screenshot tool just couldn't capture it in this environment. Reverted every piece of temporary diagnostic code (`window.__debugCam`, `preserveDrawingBuffer: true`) once this was confirmed, and switched the rest of this round's testing to `gsap.ticker.tick()` + direct DOM/state assertions instead of relying on screenshots for anything WebGL.
- That same rAF-starvation finding also explained an earlier false alarm mid-session: a scroll-linked header day counter appeared "stuck" across a batch of test scroll positions — turned out to be React 18's automatic batching coalescing every `setState` call in that test loop into a single flush, not an app bug. Re-ran the same sweep with a `setTimeout` yield between steps and got the correct value at every step (`01/60` → `60/60`, exactly matching the scroll-progress formula), confirming the header logic was correct all along.
- Verified the full scroll timeline both directions with the same forced-tick technique: hero → how-it-works → 60-day journey → (a deliberate text-free stretch during the camera's pull-back, matching the brief's "let the transition breathe") → dashboard intro → closing CTA forward, and the exact mirror image in reverse, with the day counter counting up and back down in lockstep — no stuck states, no hysteresis.
- Re-ran the full functional path end to end after resetting `localStorage` to a pre-Day-12 state: GitHub input → Check Proof → LinkedIn input → Check Proof → `2/2 verified` → Complete Day 12 → `localStorage` updated (day 12 added, streak incremented, current day advanced) → `/dashboard` reflecting the new streak and progress, including its own scroll-linked count-up animation reaching the correct final numbers once scrolled into view.
- Confirmed zero horizontal overflow across the full scroll range on all three routes at 390px, and that the only buttons left anywhere in the app are the four the brief named as non-negotiable (`Start the challenge`, `Open Day 12`, the two `Check Proof` buttons, `Complete Day 12`) plus the required external model-credit attribution links — no leftover "Next"/"Continue"-style navigation buttons.

## Round 10 brief — "the current scroll experience is good, finish the product around it"

A 35-part brief that opened with an explicit reversal of tone from every prior round: the scroll architecture was declared good and under a hard "DO NOT REDESIGN OR REPLACE" order — no rebuilding it, no click-through slides, no scroll-snapping, no touching the camera choreography "unless there is a genuine technical bug." What it actually asked for sat on top of that foundation: the site should feel like "a complete, real product," not just a 3D demo with some text over it, and named specific gaps — the city/laptop/drone visuals, dashboard functionality, and a proper small footer/navigation layer connecting the three routes into one coherent product.

Audited the brief against the actual current state before writing any code, per its own repeated "do not rebuild" instruction. Almost everything it described as missing (real GLTF city/laptop/drone, scroll-driven camera, GSAP/Lenis architecture, no Enter-City button, Sora/Inter/JetBrains Mono typography) was already built in prior rounds and left untouched. The genuine gaps were narrower: no persistent way to navigate between the three routes, Landing's footer was a single copyright line instead of the small utility tier the brief described (site links, contact, social, a "today's proof" status), and Dashboard had no build-history section. Scoped the round to exactly those three additions and touched nothing in `CityScene.jsx`, `cityCamera.js`, `LaptopScene.jsx`, `DroneScene.jsx`, or any `useScrollTrack`/`GsapScene` internals.

- Built `SiteNav` (Home/Dashboard/Today, active-route highlighting) and wired it into `PageHeader` (used by Dashboard and Day 12) and Landing's own header — small mono links, `pointer-events-auto` scoped narrowly since Landing's header sits inside an otherwise `pointer-events-none` overlay. Gave it an `orientation` prop (`row` | `column`) rather than letting a caller pass conflicting Tailwind alignment classes through `className` — two utilities like `items-center` and `items-start` both landing in the same class string doesn't reliably resolve the way JSX order suggests, since Tailwind's generated CSS order (not source order) decides the cascade winner.
- Rebuilt Landing's footer from a single `© ABTalks` line into brand blurb + site links + contact (`mailto:hello@abtalks.in`) + social, plus a compact "today's proof" line reading real `useStudentState()` data — `GitHub ✓ · LinkedIn ✓` if today's day is already complete, a real `Submit today →` link into `/day/:day` if not. Rendered Instagram/LinkedIn as plain text rather than links: ABTalks isn't a real company, and inventing a plausible-looking social URL for a fictional brand isn't something to do even as a mockup.
- Added a small `buildHistory` mock array and a 7th Dashboard scene between Achievements and the closing CTA, using the exact same `GsapScene` pattern as every other beat on the page — required rebalancing all six existing scene start/end ranges and bumping `TRACK_HEIGHT_VH` from 620 to 720 to make room, which is the one place this round touched scroll-timing math, and only to insert a new beat cleanly, not to change how any existing beat behaves.
- Re-ran the full verification pass from last round (forced `gsap.ticker.tick()` after `lenis.scrollTo(..., {immediate:true})`, since this session's browser tab still reports `document.hidden` most of the time and suspends real scroll-linked rAF ticking) across all three routes: confirmed every existing scene still fires at its same progress range unchanged, the new Dashboard scene slots in cleanly at the right point without disturbing its neighbors, and zero horizontal overflow at 390px including the new multi-column footer and the header's added nav row — checked via direct `getBoundingClientRect()` comparisons for the header (nav sits fully clear of the day-counter on the right at 390px) rather than trusting a screenshot, since this session's screenshot tool still can't reliably capture content while the tab reports itself hidden.

## Bug report — "the city scene is not visible on the first page"

A direct bug report, separate from the numbered briefs. Investigated with `canvas.width`/`canvas.height` and `gl.readPixels()` (established last round as more reliable than screenshots in this environment) rather than assuming another screenshot-tool artifact, since the last round's SiteNav addition had just made cross-page navigation a normal thing a real user would do for the first time.

- First finding: a genuinely fresh page load of `/` always rendered correctly (confirmed repeatedly across brand-new browser tabs) — the canvas landed at its real, DPR-scaled size every time. The bug only reproduced after a SECOND `<Canvas>` mounted in the same tab, whether via a hard reload or, critically, a real client-side navigation through the new nav links (Landing → Dashboard, Dashboard → Day 12, etc.) — confirmed by dispatching an actual `.click()` on the rendered `<Link>` elements, not just the `navigate` tool.
- Root-caused two compounding issues rather than patching the symptom: (1) `useGLTF`'s cache is keyed by URL only, shared globally across every `<Canvas>` in the app — but `city.glb` and `laptop.glb` are each loaded by two independent Canvases (`CityScene` and `LaptopScene`), so the second one to mount could receive a cached `Object3D` whose GPU buffers were uploaded to the first, already-disposed context. (2) A `<Canvas>` mounting immediately as the previous route's Canvas is torn down can hit a transient `THREE.WebGLRenderer: Context Lost.` — confirmed via console — during setup; the renderer recovers on its own (`gl.isContextLost()` returns `false` shortly after), but nothing re-triggers R3F's resize logic afterward, leaving the canvas stuck at the browser's 300×150 default.
- Fixed both: `useGLTF.clear(url)` for both shared model URLs on `CityScene`/`LaptopScene` unmount (forces a fresh parse for whichever Canvas mounts next — cheap, since the `.glb` itself is still HTTP-cached, no re-download), a `resyncSizeOnContextRestore` `onCreated` handler on all three Canvases that re-measures the container and calls `state.setSize()` explicitly (both immediately and on a later `webglcontextrestored` event, since which one actually catches the race is non-deterministic), and a `useDeferredMount` hook that holds each Canvas back by one tick after its own component mounts, giving the previous route's context teardown a moment to actually finish first.
- Iterated through three attempts before landing on the fix above — an initial version that only listened for `webglcontextrestored` never fired in some repro runs (the loss could apparently race ahead of `onCreated` itself), and a version that compared against R3F's own `state.size` before calling `setSize()` skipped the fix entirely in cases where `state.size` already reported the correct value while the actual canvas backing store hadn't caught up. Diagnosed both dead ends with a temporary `window.__resyncLog` array capturing container size / `state.size` / canvas size / `isContextLost()` at each step, removed before committing.
- Stress-tested with a scripted multi-hop sequence (Home → Dashboard → Today → Home → Dashboard → Today, via real `.click()` calls on the nav links) across several fresh tabs; residual context loss can still occur under rapid repeated navigation specifically in this sandboxed browser environment (plausibly a low GPU-context/VRAM ceiling under software rendering, not something a real user's hardware would hit for three lightweight, already-optimized models) — the fixes reduce it substantially and fully resolve the reported scenario (a direct, fresh load of `/`), which was confirmed working via `gl.readPixels()` returning real non-zero city geometry and a full screenshot showing the rendered skyline.
